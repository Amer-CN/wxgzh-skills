# 微服务从单体拆分：我们的决策路径与踩坑记录

> 三个月把一个 5 万行的单体 Node.js 服务拆成 12 个微服务，记录关键决策和教训。

## 背景数据

:::facts title="系统现状"
- 代码行数: 52,000 行
- 部署频率: 每周 1 次
- 平均变更到上线: 3 天
- P0 故障: 每月 2 次
:::

## 方案选择

:::decision title="拆分策略"
@recommended: 按业务域垂直拆分
@option: 按业务域垂直拆分 | 团队边界清晰，但迁移成本高
@option: 按技术层水平拆分 | 迁移成本低，但耦合风险大
@reason: 团队已按业务线组织，垂直拆分与团队结构对齐
:::

## 执行步骤

:::steps title="拆分执行流程"
1. 建立领域模型和服务边界
2. 抽取共享库和公共依赖
3. 逐个迁移业务域到独立服务
4. 配置 API 网关和服务发现
5. 灰度切流并验证
:::

## 迁移检查

:::checklist title="迁移前检查"
- [x] 领域模型已评审
- [x] 服务边界已确认
- [ ] 数据库拆分方案已定稿
- [ ] 回滚预案已准备
:::

## 常见问题

:::faq title="拆分 FAQ"
@q: 拆分后性能下降怎么办？
@a: 先用 API 网关的批量聚合减少调用数，再逐步优化热点路径。

@q: 数据库怎么拆？
@a: 按业务域拆，先做读写分离，再做垂直拆表。
:::
