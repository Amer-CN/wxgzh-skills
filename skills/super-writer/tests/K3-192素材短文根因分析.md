**P0根因：素材获取与文章写作是两个独立的人工步骤，没有数据传递。**

## 3. 素材获取链路

### 3.1 用户输入
- 主题：Kimi K3 发布
- 要求：用 AIHOT 获取全部信息，翻页，喂给写作 skill

### 3.2 调用链

```
用户操作 "发一篇关于kimi K3的文章，先用AIHOT获取信息"
→ run_skill("aihot")  # 加载 AIHOT skill 规则
→ bash: curl https://aihot.virxact.com/api/public/items?q=Kimi%20K3&take=100
   → 返回 3 条（错误：未加 mode=all，未翻页）
→ 用户指出应该能获取~200条
→ 多次尝试：q=Kimi (6条), q=K3 (5条), q=月之暗面 (2条), mode=all (200条, 但大部分无关)
→ 用户给出操作指南后：
→ bash: q=K3&mode=all&take=100 → 翻3页 → 217条
→ bash: q=Kimi+K3&mode=all&take=100 → 翻2页 → 去重合并后 192条
```

### 3.3 数据源
- 唯一数据源：`https://aihot.virxact.com/api/public/items`
- 接口返回字段：`id`, `title`, `summary`(100-300字), `url`, `source`, `publishedAt`, `score`
- 无全文抓取，无 RSS 直接解析，无数据库存储

### 3.4 "192条"的真实含义
- 192 = 两次搜索（`q=K3` + `q=Kimi+K3`）的 `mode=all` 结果，按 `id` 去重后的数量
- 其中 `q=K3` 匹配了大量无关内容（如包含"K3"字母的其他产品），`q=Kimi+K3` 才是精确匹配
- 精确匹配 Kimi K3 的条目约 30 条（score ≥ 60 的高质量条目）

## 10. P0/P1/P2 根因

### P0：192条素材从未进入写作流程（直接原因）

**证据：**
- writing-brief 素材数写的是"3条精确匹配+3条相关"（第16行）
- material-ledger 只包含 ~50条标题摘要，没有完整 summary
- 192条原始数据未持久化保存（无CSV/JSON文件）
- 写作时未调用 AIHOT API 重新获取数据

**发生位置：** material-ledger 创建环节 → 写作环节

**影响：** 192条素材全部丢失，写作仅基于 ~50条标题摘要

**对字数的影响：** 高质量素材不足导致文章内容单薄，仅1475中文字符

**确定程度：** 确定 ✅

### P1：错误使用 medium 模式而非 material_synthesis 模式（直接原因）

**证据：**
- writing-brief 指定 `article_mode: medium`, `target_visible_chars: 2500`
- Super Writer length-policy.md 第39行：material_synthesis 模式 target=6000, min=5000, max=8000
- 素材超过100条时应触发 `needs_mode_selection`（第73行），但未触发

**发生位置：** Phase 1 写作简报

**影响：** 目标字数被设为2500（medium 的 acceptable_min），而非 material_synthesis 的6000

**对字数的影响：** 直接导致目标字数偏低约60%

**确定程度：** 确定 ✅

### P2：写作基于人工记忆而非数据管道（系统原因）

**证据：**
- 写作时未加载任何 AIHOT API 返回的原始数据
- 文章基于 material-ledger 的标题摘要和我对会话历史的记忆
- 数据在 material-ledger 和写作之间没有任何程序化传递

**影响：** 素材利用率极低，大量细节信息丢失

**对字数的影响：** 间接影响

**确定程度：** 确定 ✅
